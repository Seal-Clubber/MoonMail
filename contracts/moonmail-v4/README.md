# MoonMail V4 sealed-delivery prototype

This **unpublished prototype** extends the single V3 template with an opaque sealed-letter directory. The deployed V3 source and addresses remain unchanged. The website does not select this template yet.

`publish_sealed(id, payload)` accepts a 64-digit lowercase hex ID and an opaque envelope. The current writer uses `mm-sealed-2`: one padded encrypted body and two indistinguishable wrapped-key slots for recipient and recoverable Sent access. The original four-field `mm-sealed-1` prototype remains readable by its original test helper. Neither format accepts public recipient IDs, recipient keys, recipient controller keys, capsule locators, reply IDs or conversation IDs. Storage is immutable; duplicate IDs and calls against the wrong component kind fail. Discovery pages have a maximum of 50 entries; both directories share the 4,096-letter capacity.

The contract records the transaction signer as the public sender. The browser ciphertext binds that sender in authenticated data; a copied ciphertext published by a different signer fails decryption. Sender visibility remains.

The browser prototype encrypts addressing, key version, message and optional reply identity together. Ciphertext is padded to one of five size buckets. V4 postboxes keep up to sixteen contiguous key versions and recovery references; rotation cannot silently discard historical access. Recovered keys can trial-decrypt a bounded page without fetching a recipient-specific index. Reply identities derive from the recovered mailbox secret and an encrypted random conversation nonce. A later Sent seed triggers a revisit of earlier reply pages. This is encryption-key separation, not independent Sapient spending accounts.

**Limits:** the contract validates structure and storage bounds, not whether ciphertext will decrypt. Transaction signers, timing, shared office and size buckets remain observable. Native private payments are separate from this directory; no atomic private gift or claim is implemented here. The separate reader/writer, memory-only capsule recovery, Sent and reply discovery are implemented behind a disabled evidence gate. Main UI integration, independent stock-wallet recovery and live publication/receiving tests remain required before activation. No anonymity claim. See the [protocol and threat model](../../docs/sealed-mail-protocol.md).

The engine suite includes malformed/public routing fields and access slots, duplicates, mutation, bounded paging, key history and actual browser Inbox/Sent recovery through native persisted V4 state codecs. Supply `GHOSTDROP_TEST_NODE`, `GHOSTDROP_TEST_LOADER` and `MOONMAIL_SEALED_FIXTURE` (the absolute `tools/sealed-engine-fixture.ts` path) for the SDK bridge test. It uses clearly public synthetic test keys and never touches a wallet or broadcasts.
