# Sapient wallet integration

The website's wallet is [Sapient](https://sapient.tari.mw/), an Ootle browser extension. Visitors use GhostDrop and their normal Sapient wallet. The page detects Sapient's injected provider, asks for the selected account, and sends transaction requests to the wallet's approval popup. Financial seeds and signing keys stay in Sapient. There is no GhostDrop daemon, proxy, extra extension, credential entry or file import.

Public letters, private-link decryption and prepaid guest claims still work without connection. Connecting optionally provides the selected account and public receiving address. Switch accounts or networks in Sapient; reconnect GhostDrop after a change.

## Supported interface

The adapter follows [Sapient's official integration documentation](https://github.com/chironbuilds/tari-wallet/tree/7ad3c4f117a76c64d472fd371b7d75bbe297abec/docs/integration), source commit `7ad3c4f117a76c64d472fd371b7d75bbe297abec`, version 0.6.6. The funded verification used an unmodified source build. A subsequent download from the official Chrome Store update service supplied version 0.6.6; all seven JavaScript, CSS and WASM runtime assets matched that source build byte for byte. The downloaded package passed connection, read, approval recovery and rejection against the actual published site, loaded unpacked in an isolated automation browser. The Chrome Store installation UI itself was not automated. Runtime checks reject providers lacking transaction requests or receiving addresses; no runtime version is invented from the provider's name. [Package and hosted evidence](sapient-hosted-evidence.json).

- Discover `window.tariProviders` or `window.tari` with `info.rdns === "mw.tari.sapient"`; handle late provider announcements.
- Check `tari_getNetwork` before `tari_requestAccounts`, then verify the selected component and checksummed public address. Esmeralda and Igor are supported by this adapter.
- Check `tari_getCapabilities`; recheck network, account and address before signing or resuming. Account-change events invalidate the session and clear private page state.
- Simulate through `tari_signAndSubmitTransaction` with `dryRun: true`. Require an accepted result and `finalize.total_fees_required` within the cap.
- Journal an uncertain attempt before `tari_createTransactionRequest`. Supply the original main instructions and inputs, an explicit `maxFee`, and enforced transparent fees. Sapient builds its own fee instructions and signs with its selected account.
- Save the public request ID and account before polling. Submit only the same approved ID through `tari_submitTransactionRequest`; recover its persisted status through `tari_getTransactionRequest` after reload. Never create a replacement for an uncertain submission.
- Disconnect locally and call `tari_disconnect` to remove the origin grant.

The journal contains public IDs, not seeds, private links, plaintext or encryption keys. A lost request-creation response remains blocked without a known wallet request ID. A failed/submitting wallet request is still uncertain: inspect wallet and chain history before a replacement. Sapient's SDK can internally retry input/version failures; `maxFee` is a per-transaction cap, not a guaranteed total across these wallet retries. GhostDrop does not add retries of its own.

## Verification and write gates

[Public verification record](sapient-connection-evidence.json): connection approval, real public registry reads through Sapient, draft preservation, a persisted request surviving reload, wallet rejection reconciled by GhostDrop, and origin disconnect. Both localhost and the actual Pages HTTPS origin passed. The HTTPS test substituted the reviewed local static assets in that isolated browser; no public RPC or wallet was mocked. It does not prove the changed source is published. The test request was intentionally rejected, and **zero public transactions were broadcast**.

Client tests additionally cover wrong network/account, fee rejection, lost creation/submit responses, reconnect, session invalidation and preventing gift-paid claims from being replaced with wallet-paid operations. Desktop/mobile regressions exercise the updated dialog and unchanged guest routes.

The subsequent [funded Esmeralda proof](sapient-esmeralda-evidence.json) received exactly 1 test TARI from one existing public gift into a fresh Sapient account without wallet connection, then published one text-only public letter through the stock wallet popup. The complete chain letter and persisted request's submitted status were verified after reopening the wallet. The successful receipt charged 5,092 µTARI; an earlier fee-committed/main-rejected input-discovery attempt charged 1,091 µTARI. Three other attempts aborted without fees. Aggregate wallet spend was 6,183 µTARI, below the 100,000 µTARI per-attempt cap and the one-gift total budget. No new faucet funding or replenishment occurred.

The final source declares registry, account, native resource and funding vault inputs upfront. A real Sapient dry run of this change accepted in one dry-run POST at 5,016 µTARI, followed by wallet rejection; a submission guard and unchanged balance verified zero additional public transactions. This improvement was not followed by another funded publication. Other wallet input/version retries remain possible.

`sapientWallet` is true in the published public configuration, enabling the Sapient sender route. Legacy `daemonScopes` and `httpsWallet` flags do not authorize Sapient. Existing chain and guest evidence stays enabled. No contract redeployment is required. The funded proof used the Pages HTTPS origin with local app/config overrides; subsequent hosted checks verified commit `cd49dbc`, successful Pages/Verify workflows, all seven matching production assets, desktop/mobile reading and the official store package's connection and approval recovery without asset overrides. Only a text-only public publication was broadcast through Sapient; private-link encryption/gift rules retain their separate prior evidence, while Sapient private-link and gifted publications were not separately broadcast in this bounded proof.

## Postbox recovery remains incomplete

The prior [native memo adapter](STANDARD-WALLET-POSTBOXES.md) requires a permanent, script-only `DenyAll` output and access to its historical decrypted memo after wallet restoration. Sapient's provider rejects raw `StealthTransfer` instructions. A subsequent [contract capsule candidate](SAPIENT-POSTBOX-RECOVERY.md) passed the real local 0.45 engine and stock Sapient backup-restoration tests: a normal contract call creates a custom-resource encrypted memo, and Sapient recovers it through a deterministic resource/commitment lookup. Both wallets decrypted the example addressed letter; a foreign wallet failed. The wallet reads used engine fixtures, so this is not public testnet recovery evidence or an enabled production adapter.

The core recovery adapter now verifies permanent ledger rules, reads the deterministic custom output through Sapient, rechecks account/view permission and opens letters with authenticated capsule references. Its actual code passed an independent backup-restoration lab. Creation uses a normal contract call and a public-only journal; reload resumes the same wallet approval, and unknown results block replacement keys. The gated UI now explains account-wide private view access and requires explicit consent. Historical descriptors and their encryption context are preserved. Full funded creation, registered rotation/history, public deployment and lost-response verification remain incomplete. New addressed mail and postbox setup remain gated. Sapient addressed gift creation/collection stays separately blocked even if capsule evidence is later enabled.

Addressed gift claims also require caller-supplied fee instructions that Sapient's current API does not preserve; its SDK builds account-paid or private-UTXO-paid fees instead. The existing gift checkpoint must not be silently replaced. A browser-only local key, a public-signature-derived key or an ordinary spendable memo cannot satisfy the original recovery requirement. No custom wallet build or extra local program is the visitor solution.

Legacy daemon code remains for optional donor/deployment tools and historical verification. It is not the website's connection route. The older [manual manifest candidate](WALLET-HANDOFF.md) is superseded for the current Sapient target.
