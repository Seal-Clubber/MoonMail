# Architecture and threat model

> Historical design/evidence notes: the current release uses the V4 sealed office as its single default. Old testnet offices are not selectable or migrated. See [current private-email capabilities](private-email.md), [sealed protocol](sealed-mail-protocol.md) and [verified private payments](private-payments.md). Dated results below apply only to their recorded build.

MoonMail is a static React application. GitHub Pages serves HTML/CSS/JS and the official Tari crypto WASM. There is no required MoonMail server. The website connects directly to Sapient's injected browser provider; indexer reads and guest transaction submissions go directly to replaceable infrastructure. Optional donor/deployment tools and preserved historical recovery code retain their daemon adapter.

## Authority and data

The Rust PostOffice template stores postbox IDs/nicknames/controllers/encryption public keys and a stable ID-to-envelope component index. It atomically creates a separate Envelope component containing the complete public message or authenticated ciphertext, immutable claim authority and its own funded vault. Link envelopes have a public claim verification key; addressed envelopes freeze the registered controller. Each component uses OwnerRule::None, disabling owner access-rule changes. No upgrade/withdraw/refund route or administrator exists. Sending withdraws exact gift plus reserve and publishes in one main intent. Sender publication fees can still commit when publication fails; reconcile the transaction and account balance before trying again. Separate envelope components prevent later registry growth from increasing an existing gift's claim storage cost or making unrelated gifts compete for the same registry write lock.

Only native test TARI is implemented, with **revealed** gifts and fees. Do not confuse this with L1 Universe XTM, or claim confidential gift amounts. Transaction sender/controller keys, timing, resource, amounts, envelope IDs and addressed routing remain visible.

## gd-link-1 cryptography

The device generates a random 32-byte root capability using Web Crypto. HKDF-SHA256 derives two independent AES-256-GCM keys with distinct `letter` and `claim-wrap` labels. Salt, info and authenticated data bind version, network, registry, template, envelope ID and purpose. Fresh 12-byte IVs are used separately for each encryption. The entire subject/body is encrypted.

The claim signer is a separately random keypair from official Tari WASM `generateKeypair`, wrapped under the `claim-wrap` key. This construction deliberately does not invent a scalar derivation from HKDF bytes. Opening unwraps the private scalar, verifies its derived Tari public key against the recorded authority, and delegates transaction signing to the official SecretKeyWallet. The random root and wrapped signer are independent; no financial wallet seed is imported or exported. This is a standard primitive composition tested here, **not a third-party cryptographic audit**.

The capability stays in the fragment and page memory. It is never an RPC argument, query, analytics event or on-chain field. Capturing replaces the visible history entry with an ID-only route. Refresh after capture needs the saved original link again. Anyone with the original link, including the sender, can read and compete to claim. A malicious frontend/extension can steal it. AES authentication does not hide public metadata. Claimed letters remain decryptable.

In an already-open tab, history navigation can deliver both `popstate` and `hashchange`. The first captures and scrubs the complete private route. The hash handler ignores a queued event whose `newURL` no longer equals the current URL, so it cannot mistake the shortened address for another broken link. The popstate handler remains active for Back/Forward between equal, scrubbed hashes. Pasted Markdown escapes before known context-query separators are normalized; the capability and encrypted context values remain unchanged and strictly validated.

## Fee checkpoint

`claim_and_pay_fee` runs wholly in **fee instructions**: verify gift state and authority; require a built-in account destination; mark claimed; deposit exact gift; pay the fixed reserve cap. This makes the entire payout part of the fee checkpoint. A failed main intent must retain both payout and consumed claim; a fee-checkpoint failure must revert both. There is no generic fee-sponsor method that can be called repeatedly without consuming the gift. Extra instructions can burn only the cap committed to this gift; they cannot reopen it. An insufficient cap leaves the gift unclaimed. Unused reserve is permanently locked; no expiry or refund is implemented.

Engine tests validate these checkpoints. Separate isolated-network probes verified real indexer submission and independent recipient daemon discovery/spending; the intended hosted deployment still needs its own evidence before production buttons are enabled.

## Receiving and wallet credentials

The current website uses [Sapient](SAPIENT.md). Its origin/account grant exposes public metadata; each real transaction requires wallet approval. Network/account/address are rechecked, and changes clear private page state. No API key or financial seed is entered into MoonMail. Persisted wallet request IDs allow approval/status recovery after reload without repeating request creation. The wallet owns fee construction and may internally retry rejected input/version attempts; a per-transaction fee cap does not bound aggregate wallet retry fees.

Guest claims keep their original prepaid fee-checkpoint transaction, independent of Sapient's funding instructions. Sapient is optional for receiving; its public address/account can fill the destination form. Gift-funded new-account creation has independent engine and Esmeralda proof. The following daemon credential details describe the preserved tool/historical adapter, not the visitor connection.

Gift collection takes an Ootle wallet address, with no account-ID field or account-creation checkbox. The client derives the canonical built-in Account identity from the checksummed address's owner key and verifies the account template and owner through the indexer. The public-key hash uses pinned `@noble/hashes` Blake2b-256 and the engine's domain-separated Borsh encoding; three fixed vectors are checked against the current native engine. Wrong-network and memo addresses are rejected.

For public/private-link gifts, only an explicit account-not-found response enables the already-verified gift-funded account-creation path, and only when deployment evidence enables it. The engine's CreateAccount instruction uses the existing canonical account if it appeared in the meantime. Outages, timeouts and malformed/mismatched accounts cannot trigger this fallback. A read-only review precedes a separate collection confirmation; the sender's reserve pays collection/setup fees. Public/link claims keep ephemeral/link signers and need no wallet connection. Postbox claims retain Sapient's ownership proof and require an existing destination. Mailbox authority and destination ownership remain separate. Indexers see the account lookup; this change does not hide recipient or gift metadata.

The wallet adapter uses official `authenticateWithApiKey`, disables reauthentication, validates network and paginates accounts. API keys stay in memory and are cleared on disconnect. A key permitting arbitrary submission is spending authority. Source and isolated daemon 0.43.0 probes confirm `transactions:create` is unscoped; older permission names are rejected. No Admin permission is requested. Read-only keys list accounts but fail actual submission; expired/revoked keys fail account operations. Dry-run signing is allowed with read scope and must not be described as a no-signing permission. Actual isolated publication/account signing and separate recipient spending passed; repeat against the intended deployment and HTTPS origin.

## Mailbox recovery boundary

**Current Sapient status:** postbox writes, addressed mail and addressed claims remain disabled. The stock provider has not proved permanent memo carrier creation or historical key recovery; the following native-memo and legacy-extension evidence is preserved without claiming Sapient compatibility. See [the precise blocker](SAPIENT.md#postbox-recovery-remains-incomplete).

New keys use the [standard-wallet memo adapter](STANDARD-WALLET-POSTBOXES.md). The browser generates a random mailbox key and sends it to its controlling wallet in an ordinary encrypted native memo on a script-only `DenyAll` output worth 1 µTARI. The financial seed and private view key stay in the daemon. Account-scoped `stealth_utxos.list` returns decrypted memos, including the mailbox key, to page memory. MoonMail verifies the output is on chain, has the exact script-only condition root and value, and matches the complete context and published public key. The key never enters browser storage. That permission can also reveal other private payment memos within the granted account.

Sender encryption combines official Tari ephemeral Ristretto DH, domain-separated HKDF-SHA256 and AES-256-GCM; authenticated metadata binds network, registry, template, postbox, controller, key version, envelope ID and both public keys. Complete subject/body ciphertext remains on chain. The optional `recovery: native-memo-1` descriptor/payload field selects the adapter; it does not replace authenticated context or key verification. Unmarked historical keys retain the [legacy extension](../wallet-extension/README.md) path rather than silently changing secrets.

Earlier native extension tests and actual RPC/browser tests prove historical recovery for that legacy path. Standard-memo proof separately restores an unmodified wallet and opens an actual chain letter through the new application adapter. Automated adapter tests cover historical versions, distinct postboxes, unsafe carriers, permission failures, session changes and uncertain submissions. Native creation first simulates and reads the accepted dry-run receipt under its fee cap, journals public recovery details before broadcast, then requires confirmation and a fresh memo read before registry publication. The registry transaction has its own journal and fee review. Fresh creation confirmation and the full new browser setup flow still need end-to-end verification. Public write gates remain closed until the chosen deployment and hosted transport have evidence. Imported/view-only accounts do not inherit an ordinary seed-restore guarantee.

## Infrastructure, pagination and history

The client verifies configured template identity and ownerless registry, then strictly decodes the component state returned by the indexer. It does **not** verify validator consensus proofs. A dishonest indexer can lie about history, confirmed availability and destination ownership; use infrastructure you trust and verify delivery in the recipient daemon. Template method checks and signatures still govern honest chain execution.

Configure indexer tracking for the registry, child envelope components and their dependent vaults. Registry IDs plus current envelope states are the authoritative archive, retaining full letters after claims. `list_letters(after, limit)` and `list_postboxes(after, limit)` provide stable-ID pages of 1..100 in template calls. The static client downloads the registry index and fetches envelopes in pages of 100 (eight parallel reads at a time), renders 12 per page and offers “Load more chain mail.” Direct private links resolve their ID independently of the loaded page. The keeper reads every page before planning refills. This registry index still grows; publication scalability is bounded by actual engine limits and is not an unlimited archive guarantee. Historical indexer retrieval uses explicit substate versions (`provider.getSubstate(id, version)`), subject to indexer retention. Export/mirror public configuration and use another compatible indexer to access the same post office independently of the original host.

Before a broadcast the client journals a public attempt ID; a returned transaction ID replaces it. Lost HTTP responses therefore remain uncertain and disable duplicate submissions. Confirm through the envelope's state and account/transaction history, rather than assuming a timeout failed. An attempt without a transaction ID cannot prove rejection automatically. Losing the disposable cache does not delete chain state; reconcile envelope/account history before retrying. Keeper reservations similarly retain uncertainty across restart and bind the journal to network, registry and campaign. No fee spending automation is part of the hosted interface.
