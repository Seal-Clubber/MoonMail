## Contract and recovery

[`contracts/recovery-capsule`](../contracts/recovery-capsule/src/lib.rs) creates an ownerless custom Stealth resource. Minting is permanently restricted to its capsule component. Burning, recalling and freezing are permanently denied. `store` accepts a bounded JSON string containing an encrypted output and its proofs, requires exactly one carrier unit and output, denies existing inputs and revealed change, and requires the single-leaf `DenyAll` script root with no key spending path. Ootle verifies the range and balance proofs before committing. Neither a wallet signing key nor a plaintext postbox key is submitted to the contract.

The browser generates an application encryption key and uses the recipient's public Ootle address to encrypt the existing bound `gd-capsule-1` memo. Sapient keeps its financial signing and view secrets. The new `sapient-capsule-1` descriptor retains the carrier's resource address and commitment, together with the postbox encryption public key and key version. Every sealed envelope copies that reference and authenticates it in its encryption context, so later key rotation preserves the reference for older mail. Changing or stripping the reference fails decryption. Historical descriptors retain their original encoding and encryption context.

Recovery uses a separate Sapient view-access approval, then a deterministic resource/commitment lookup. `tari_claimPrivatePayment` decrypts and remembers the custom output in the wallet; it performs local payment bookkeeping and broadcasts no transaction. Subsequent reads use `tari_getShieldedOutputs`. GhostDrop's capsule decoder checks the network, registry, template, postbox, controller, key version and encryption public key before using the recovered application key. There is no need to scan recent receipts to locate an old key. The permanent UTXO, rather than the original browser or a spendable payment memo, holds the encrypted key.

Sapient's current view approval covers the account's private output summaries, not a GhostDrop-only resource. The UI must explain this before requesting it. Financial seeds, view keys and signing keys must never be requested by GhostDrop.

## Recovery adapter

`src/core/sapient-capsule.ts` implements recovery separately from transaction submission. `SapientSession.capsuleMailbox` supplies the current wallet session and a public substate reader. Recovery requires an existing explicit view grant, validates the controlling account/network/key version, checks the current resource's immutable owner and burn/recall/freeze rules and the native output's script-only lock, then reads only the descriptor's resource and commitment. It uses the wallet's remembered memo when present; otherwise it records that deterministic private output once. It never scans recent receipts, signs a transaction or prompts implicitly for view access.

Wallet identity and view permission are rechecked before returning a recovered key or plaintext. Temporary application keys are cleared after opening; the adapter stores no decrypted memo or key in browser storage. The gated postbox UI explains account-wide access and requires an explicit checkbox and wallet approval before recovery. Setup, registration, approval resume and historical opening now call the Sapient core; public writes remain disabled.

## Creation and approval journal

`prepareSapientCapsule` generates a temporary application key, encrypts its bound memo using only the wallet's public receiving address, builds and validates the official SDK output/proofs, then clears the key. The returned data contains an encrypted statement and public descriptor only. The engine fixture now exercises this production code rather than a duplicate crypto implementation.

`SapientSession.storeCapsule` verifies the reviewed template, ownerless capsule component, immutable resource and its component-only mint authority. It includes the wallet account, fee vaults, resource and template dependencies before simulating. A positive fee cap and accepted simulation are required. Before requesting approval it journals account/context/descriptor/resource/commitment and deployment identity; no plaintext memo, application key or encrypted statement is stored in that journal. The wallet request ID is saved before polling. Reload resumes that same ID; a lost creation/submission response, rejection or previous setup blocks replacement keys. The postbox is registered only after known transaction confirmation and a fresh wallet recovery check. Native journals retain their earlier format.

The configured deployment requires a reviewed optional `capsule` object with `template`, `component` and `resource`. It has no default invented addresses. Changing networks clears it. A metadata flag alone does not enable Sapient postboxes without these identities. [Setup checks](sapient-capsule-setup-evidence.json) distinguish client fixtures from engine and stock-wallet proof. Full funded creation, registered rotation and public lost-response recovery remain unverified.

Seven client tests cover uncached/cached lookup, ledger permanence, permission denial and revocation during recovery, wallet identity, historical references after rotation, authenticated-reference tampering and legacy encoding. The [adapter lab record](sapient-capsule-adapter-evidence.json) verifies this actual core code with the unchanged official Sapient package: original and independently restored wallets opened the same reference-bearing encrypted letter. The adapter executed in the owner test process through the real browser provider; it was not a full product UI or live-chain deployment test.

## Remaining boundaries

`mailboxRecovery` remains false. The capsule template has no confirmed public template/component/resource address. Creation/journal and explicit privacy UI are implemented behind that gate, but full funded creation, registered rotation/history and public unknown-response recovery still need end-to-end verification. Reference preservation and local restored-wallet recovery are verified; full rotation through a deployed post office is not. Do not enable the gate merely because these checks passed. Public deployment or funded tests need a new bounded authorization; the prior one-letter test is complete.

There is also a separate **addressed gift claim** limitation. The current [Sapient provider](https://github.com/chironbuilds/tari-wallet/blob/7ad3c4f117a76c64d472fd371b7d75bbe297abec/src/background/index.ts) accepts main instructions, inputs and a fee cap. Its [SDK 0.1.20](https://www.npmjs.com/package/@chironbuilder/ootle-sdk/v/0.1.20) `OotleAccount.execute` path constructs its own account-paid or private-UTXO-paid fee instructions. GhostDrop's existing envelope requires `claim_and_pay_fee` in the fee phase, where payout, claimed state and the reserve payment share a checkpoint. Moving that call into main instructions is invalid: Ootle rejects fee payment in the main intent. Exporting signing keys or converting the claim to wallet-paid fees would not satisfy the original design. The current Sapient adapter therefore continues to reject such conversion.

A stock-wallet API that preserves reviewed caller-supplied fee instructions and supports their authorization could retain the deployed gift contracts. The separate [V2 proof-claim contracts](POSTBOX-PROOF-CLAIMS.md) now implement another route, with real registry/controller checks and a bounded destination-specific ownership proof. Eleven local financial engine tests and the browser adapter tests verify the new route, while new public template deployment and funded verification remain incomplete. Existing envelopes remain immutable and retain their historical claim rules. Wallet ownership/message proofs are not interchangeable with transaction authorization signatures; the V2 contract verifies the proof as its own narrowly scoped authorization.

The gift's funding source and the transaction's authorization are separate constraints. Paying fees from the gift rather than its separate reserve does not make the existing fee-phase call compatible with Sapient. A new ordinary main-phase claim could instead use Sapient's account-paid fee transaction: the recipient pays first, then receives the gift, so their net increase is gift minus fees. That simpler alternative requires an already funded wallet, a new method and verification; it is not implemented and would not provide zero-balance postbox collection. The current intended route retains zero-balance collection through a separately verified ownership-proof design.

### Ownership-proof compatibility investigation

The pinned stock provider exposes `tari_signWalletOwnershipChallenge` with an explicit wallet approval. SDK 0.1.20 signs a Blake2b-512 ownership message under `com.tari.paylink.wallet_ownership_proof.v1.v1`, with individually length-prefixed network byte, exact wallet address and challenge. Its WASM Schnorr primitive then hashes individually length-prefixed nonce, public key and message under `com.tari.schnorr_signature.v1.challenge`. The Ootle 0.45 built-in contract verifier instead hashes raw `domain || nonce || publicKey || message`; a domain string alone does not reproduce the SDK's length prefixes.

An isolated synthetic-key format probe using the stock SDK WASM verified that signature with the length-prefixed construction and rejected changes to network, address, challenge, key, nonce and scalar. Three raw native-verifier domain variants failed. This invokes no wallet provider and submits no transaction; it proves a client crypto format only, not contract execution or stock-wallet approval. [Format record](sapient-ownership-format-evidence.json) records these limits.

A separate local Ootle 0.45 engine fixture now reproduces both hashes using Blake2b-512 and native Ristretto operations. It accepted the actual stock SDK WASM signature and rejected eight cases: altered network, address, challenge or scalar; identity key or nonce; noncanonical scalar; and oversized challenge. Canonical point/scalar and identity checks precede group operations. The [engine record](sapient-ownership-engine-evidence.json) records the result and source hashes. This uses a synthetic key/address and a stateless verification primitive: it proves neither actual wallet approval nor canonical address/account binding, controller selection, replay protection or a claim transaction.

The new claim method verifies against the postbox's trusted controller key, rather than a key supplied by the claimant. Its canonical challenge binds network, registry, envelope identity, exact destination, native payout resource, gift, reserve and expiry; the canonical wallet address and verified signature bind the controller. An atomic fee checkpoint enforces the claimed flag and reserve cap and pays the exact gift. Engine tests reject replay, wrong destination, foreign controller, expired proofs, unregistered envelopes and insufficient fees, and verify payout retention after a later main-instruction failure. This is local V2 evidence; the original deployed envelopes retain their current rules.

A later [binding fixture](sapient-ownership-binding-evidence.json) uses a valid Ootle address generated and parsed by the stock SDK, with synthetic keys only. An immutable lab component stores the configured network/address/controller/challenge and accepts only nonce/scalar at verification. The Ootle engine accepts the original proof and rejects a different configured controller or destination, plus changes to the signed network, registry, envelope, resource, amount and expiry bytes. The final test contains two positives and twenty negatives. The constructor does not authenticate the real postbox registry; contract-side address parsing, canonical field semantics, expiry enforcement, replay state, payout and fees remain absent. This verifies fixed-context signature binding, not a financial claim. No stock-wallet provider is invoked.

Template publication has a related operator-side boundary: the provider's `instructions` operation does not forward transaction blobs. Its SDK represents a `PublishTemplate` binary by an index into `blobs`. Do not pass a blob index alone or assume an ignored `blobs` property will publish the binary. This does not prevent ordinary capsule `CallMethod` use after a verified deployment, but publication must use an actually supported operator path.
