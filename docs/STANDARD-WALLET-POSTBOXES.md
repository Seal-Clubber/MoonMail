# Postboxes with the standard wallet

**Historical daemon adapter.** The website now targets [Sapient](SAPIENT.md). This proof and its descriptors remain preserved, but Sapient's provider does not yet establish the permanent carrier/historical memo interface required below. New postbox setup remains disabled. Visitors are not instructed to run a daemon or a patched wallet.

New postbox keys in the local source now use the standard Ootle wallet's encrypted payment memos. Recovery has been exercised on an isolated chain using the **unmodified official wallet daemon 0.43.0**, including the new application adapter and an independently restored wallet. The hosted build has not yet received this source change, and its standard-wallet connection remains unresolved.

## Preserve the original model

1. The website generates a random mailbox encryption key for one postbox and key version. It retains the key only in page memory during memo creation.
2. Store the private mailbox key in a small **encrypted native Ootle memo**, sent to that wallet's own Ootle address. Encrypting a native memo uses the wallet's ordinary view public key; the financial seed and private view key never leave the wallet.
3. Put that memo on a one-microTARI carrier output with a script-only `DenyAll` spending condition. Its value is permanently locked, so normal spending cannot consume the recovery record. Review its fee cap separately, confirm it, and recover the matching key before signing registry registration or rotation with a second fee cap.
4. The sender encrypts the complete subject/body to the registered mailbox public key. The full ciphertext remains in the existing ownerless Envelope component. The recorded controller still governs postbox updates and addressed-gift collection.
5. On another device, restore the ordinary Ootle wallet from its seed. Its native scanner decrypts the memo. GhostDrop reads that account's recovered memo using `stealth_utxos.list`, obtains only the mailbox key, and decrypts letters in the browser.

This keeps wallet-controlled postboxes, independent nicknames/inboxes, complete on-chain letters, versioned keys and wallet recovery. It requires no separate mailbox backup file, new user identity, financial seed import into the website, custom daemon decrypt RPC, or GhostDrop backend. Public and private-link flows are unchanged.

The [official privacy documentation](https://ootle.tari.com/concepts/privacy/#encrypted-payloads) describes encrypted native payloads and memos. The pinned standard implementation returns decrypted memos in [`stealth_utxos.list`](https://github.com/tari-project/tari-ootle/blob/392d805579db35fcc8e8bc1aba84adc1fffe0c22/applications/tari_walletd/src/handlers/stealth_utxos.rs); native memo bytes are bounded to 253 bytes. A short key capsule fits; the entire letter need not fit in the memo.

## Actual proof

The test published a script-only `DenyAll` carrier, created a wallet-controlled postbox, and published a full encrypted addressed letter to the real isolated registry. It then recovered the carrier in a fresh standard-wallet store restored internally from the disposable test seed, with no original wallet database or browser key. A new process read the stored envelope through the indexer, checked its frozen controller and successfully opened its full subject/body using the application's crypto helper. Public identities and accepted transaction IDs are in [native-memo-evidence.json](native-memo-evidence.json). These addresses belong to localnet, not Esmeralda.

The carrier's committed script root matches the official WASM-derived root for the single `DenyAll` condition and has no alternate key spending path. Native wallet selection excludes script-only outputs. The creation/rotation cost includes one permanently locked microTARI per key version plus transaction fees. Do not use an ordinary spendable payment output as a recovery record.

Normal owner UI authentication issued/revoked temporary keys for creation and publication. Fresh-store recovery used an isolated loopback wallet in test-only authentication-none mode and a read-only JWT, so it proves cryptographic/native scanning recovery, not physical-passkey onboarding. No personal wallet or public testnet funds were used. The first memo scans lagged while the restored chain caught up; later original-wallet and independent restored-wallet reads both succeeded. No uncertain submission was repeated.

## Adapter integration and remaining verification

- `src/core/native-mailbox.ts` uses standard `stealth.transfer`, reads the accepted dry-run receipt under the supplied fee cap, and writes a public attempt record before the actual transfer. `Postboxes.tsx` shows both fee caps and the permanently locked carrier amount. The user checks confirmation, then separately publishes the registry update. Both steps have independent transaction journals. Reload can resume the public descriptor/context; no recovery secret or plaintext memo is stored in browser storage. An uncertain attempt blocks automatic replacement, including after an API-key change. Use one active setup client for a given postbox version; the browser journal is not a distributed transaction lock.
- Bind the capsule to the full network, registry, template, postbox, controller and key version. `src/core/capsules.ts` supplies a compact context-hashed format and checks the recovered key against the published public key. Both an early test tuple and this hardened application format pass native-wallet recovery. The final proof uses the hardened format and `openMailbox` against ciphertext freshly read from the chain. Four automated tests additionally cover context changes, public-key substitution, malformed capsule error redaction, ciphertext tampering and changed envelope IDs.
- New descriptors and ciphertext carry `recovery: native-memo-1`, selecting standard memo recovery and `openMailbox`. The original `gd-postbox-1` cryptography and authenticated context stay unchanged. Unmarked historical postboxes retain their compatible legacy adapter; their keys cannot silently change. Before publishing a new key, the chain client re-reads the actual native carrier and verifies its value, script-only root, full context and public key.
- Adapter tests cover historical versions and distinct postboxes, unsafe/foreign carriers, published-key binding, denied memo reads, session changes, lost responses, overlapping dry runs and over-cap/unreadable simulations. An actual fresh process using the independently restored stock wallet opened the complete earlier chain letter through this adapter. Reading native memos can expose other private payment memos within the granted account; grant that account's `stealth_utxos:read` deliberately. Creation needs `transfer:create` and `transactions:read` for simulation/confirmation; registry updates need `transactions:create`. None implies a narrower transaction-spending authority than the daemon actually enforces.
- Resolve the **actual GitHub Pages-to-standard-wallet connection**. The cryptographic proof uses local RPC. A credential-free Pages-origin OPTIONS probe against the unmodified 0.43.0 daemon returns HTTP 200 with no `Access-Control-Allow-Origin` or `Access-Control-Allow-Headers`; the current direct authenticated fetch adapter therefore cannot connect under stock defaults. Native WebRTC exists, but a complete supported hosted pairing flow and its signaling infrastructure have not been verified. Browser local-network permission alone does not fix CORS. Do not require an additional user-side process, add a central wallet proxy, enable permissive development CORS, or claim hosted connectivity based only on the crypto test.

A new adapter creation probe passed standard-wallet dry-run/receipt checks and submitted **8278fb28f5ee11334206234eb1cbb63efddf44aa15436863794f554fb78467c5** with a 1,000,000 µTARI cap on isolated localnet. Confirmation remained pending because the restored validator was hundreds of epochs behind its configured clock. Its public journal is preserved, the temporary key was revoked, and no replacement was broadcast. Do not count that probe as confirmed setup or new-mail publication. Reconcile it after safely catching up the saved test chain; then verify new creation, rotation and the complete browser setup sequence.

The public deployment's `daemonScopes`, `httpsWallet` and `mailboxRecovery` flags remain false. This source integration and recovery proof do not establish authenticated hosted connectivity or a complete standard-wallet browser flow.

## Connection investigation

The official [`ootle-wallet-daemon-signer`](https://github.com/tari-project/ootle.ts/tree/main/packages/ootle-wallet-daemon-signer) creates a `WalletDaemonClient.usingFetchTransport`; its browser support assumes that the daemon endpoint is reachable with the required browser permissions and CORS policy. Installing this SDK in the page does not change the daemon's response headers. Its authentication helper defaults to Admin, so any future integration must supply explicit account-scoped permissions instead.

The pinned stock wallet contains a WalletConnect implementation, but [`LayoutMain.tsx`](https://github.com/tari-project/tari-ootle/blob/392d805579db35fcc8e8bc1aba84adc1fffe0c22/applications/tari_walletd/web_ui/src/theme/LayoutMain.tsx) comments out its UI entry. Its [`WalletConnectLink`](https://github.com/tari-project/tari-ootle/blob/392d805579db35fcc8e8bc1aba84adc1fffe0c22/applications/tari_walletd/web_ui/src/components/WalletConnectLink/WalletConnectLink.tsx) also declares only `tari:devnet` and does not forward `stealth_utxos.list` or native stealth transfers. Those files were checked against the pinned upstream commit without local modifications. This is not a working Esmeralda/native-memo pairing route in the standard release.

The native WebRTC implementation needs a separate HTTP signaling service at the daemon's configured socket address. An existing supported pairing service has not been established by this work. A custom signaling server or user-side proxy would change the requested architecture. Next work should establish a supported wallet connection that allows only the approved website and account-scoped operations, then exercise the complete hosted adapter. The recovery proof does not require modifying the wallet's cryptography.

On 2026-10-06, official releases 0.44.0 and 0.45.0 were checked for connection changes. Source inspection of [0.45.0 server.rs](https://github.com/tari-project/tari-ootle/blob/v0.45.0/applications/tari_walletd/src/server.rs), [config.rs](https://github.com/tari-project/tari-ootle/blob/v0.45.0/applications/tari_walletd/src/config.rs) and [LayoutMain.tsx](https://github.com/tari-project/tari-ootle/blob/v0.45.0/applications/tari_walletd/web_ui/src/theme/LayoutMain.tsx) still shows default empty CORS, a development-only permissive switch, external signaling configuration and the commented WalletConnect entry. This is source evidence, not a new 0.45.0 authenticated hosted runtime test. No financial wallet SDK or daemon version was silently upgraded. Guest collection on the actual Pages site works independently of this dependency.
